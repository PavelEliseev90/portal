# Соглашения по UI портала (`portal-style.css`)

Живая витрина компонентов и краткий обзор: страница **`/dev/styleguide/`** (нужна авторизация в портале).

## Скоуп страницы

1. **Корень контента** — обёртка с классом **`portal-page`**. На ней держатся отступы и фон секции контента. Внутри неё размещают блоки страницы.
2. **Заголовок экрана** — **`portal-header`**: заголовок (`h2`) и подзаголовок (`p`). Не смешивать с шапкой сайта в `base_web.html`.
3. **Секции-карточки** — **`portal-panel`**: белая панель с тенью и скруглением. Внутри — сетка Bootstrap, таблицы, формы. Вложенные `portal-panel` допустимы, но лучше избегать глубокой вложенности без необходимости.
4. **Глобальные селекторы** в `portal-style.css` не добавлять без крайней нужды (например, `table { ... }` без префикса). Предпочтительно: **`.portal-panel .table`**, **`.portal-page ...`** и т.п., чтобы не ломать сторонние страницы и виджеты.
5. **Bootstrap** — для сетки, кнопок, форм, алертов использовать стандартные классы Bootstrap; в `portal-style.css` — только портальная «надстройка» (панели, метрики, специализированные карточки).

## Именование классов

1. **Префикс `portal-`** — для общесистемных блоков макета: `portal-page`, `portal-header`, `portal-panel`, `portal-sidebar`, а также метрик в «плоском» виде: `metric-card-label-portal`, `metric-card-value-portal`, `metric-card-portal`.
2. **kebab-case**, латиница, без пробелов.
3. **Суффикс `-portal`** у метрик — каноничный вариант для новых и переписываемых экранов. Классы **`metric-card`**, **`metric-card-label`**, **`metric-card-value`** (без суффикса) считаются **наследием**; в новом коде по возможности не использовать; при правках страницы — по возможности переводить на вариант с `-portal`.
4. **Страницы с особым лейаутом** (настройки, матрицы и т.д.) могут использовать собственные корневые классы (`settings-page`, `matrix-page`, …), уже описанные в `portal-style.css`. Новые такие страницы именовать по шаблону **`<область>-page`** и группировать связанные **`-header`**, **`-panel`**, **`-filter`** в одном месте файла стилей.
5. **Компонентные блоки** без префикса `portal-` допустимы, если это узкий переиспользуемый блок (`car-spec-card`, `settings-chip`, `cost-badge`). Им дают **говорящее** имя предметной области, избегая слишком общих слов в одиночку (`box`, `block`, `item`).

## Где писать стили

1. **Источник правды** — файл **`static/css/portal-style.css`** (подключается из `base_web.html`).
2. **В шаблонах тег `<style>`** не добавлять для типовых компонентов. Исключения: одноразовый прототип (с последующим переносом) или стили, завязанные на **динамические** значения из контекста (редко).
3. При добавлении блока в стилевой гайд — **по возможности** добавить тот же паттерн в раздел демо на `/dev/styleguide/`, чтобы следующий разработчик видел эталонную разметку.

## Порядок слоёв (каскад)

Подключение в базе: `style.css` → **`portal-style.css`** → Bootstrap и плагины. Учитывать, что переопределения Bootstrap должны жить в `portal-style.css` с **достаточной специфичностью** (например, `.portal-panel .form-control`), а не «голым» `.form-control`, если это не сознательное глобальное правило.

## Версионирование

При изменении внешнего вида существующего класса из гайда проверять **все** шаблоны, где он встречается (поиск по проекту). При ломающем изменении лучше ввести **новый** класс и мигрировать страницы порциями.
