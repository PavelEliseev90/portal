# Проект: Речевая аналитика диктофонов (KG Speech)

**Статус:** планирование / старт реализации  
**Дата старта оформления:** 2026-07-31  
**Границы:** только диктофоны + РЛК. CVC (`audio-control.by`) **не трогаем** — отдельный контур.  
**Цель бизнеса:** понять, как менеджер общался с клиентом: всё ли предложено, корректность речи, полнота скрипта/чек-листа.

Связанные материалы:
- **Презентация (HTML):** [`docs/presentation/speech-analytics-dictaphone.html`](presentation/speech-analytics-dictaphone.html) — для руководства и демо  
- **Canvas:** `speech-analytics-dictaphone.canvas.tsx` (в Cursor рядом с чатом)

## 1. Зачем проект

| Вопрос | Как отвечаем |
|--------|----------------|
| Что сказал менеджер клиенту? | Полная расшифровка с таймингами |
| Всё ли предложено (трейд-ин, кредит, тест-драйв…)? | Чек-лист + тематики по тексту |
| На каком моменте сработало? | Цитата + `time_start` / `time_end` |
| Как улучшить распознавание терминов? | Словарь → пересборка модели (Debian) |
| Кто говорит в mono? | Отдельный этап (сложно) — см. §8 |

---

## 2. Принципы

1. **Офлайн** — STT на своём сервере/ПК, без интернета для распознавания.  
2. **Портал** — загрузка, РЛК, настройки, UI, скоринг, отчёты.  
3. **STT-машина** — отдельно от веб-сервера портала (как раньше с Vosk).  
4. **CVC не ломаем** — параллельный внутренний контур «KG».  
5. **Сначала диктофоны**, телефония — позже по тому же паттерну.  
6. Каждый релиз сверяем с чеклистом «хотели → сделали» (§10).

- `Records_voice_recorder_cvc_*` — **чужой** контур CVC (не меняем в этом проекте)

### Этап 1 — STT-воркер под очередь РЛК (R1)

**Хотели:** офлайн полная расшифровка фрагмента визита с таймингами.  
**База:** старые скрипты Vosk + `get/post_records_queue`.

Задачи:

1. Воркер на STT-ПК: poll `get_records_queue`, скачать/открыть аудио, trim по `time_start`/`time_end` относительно начала файла.  
2. Vosk `SetWords=True`, нормализация аудио, стабильные temp-файлы.  
3. Контракт JSON (единый):

```json
{
  "id": 0,
  "info_model": {"name": "vosk-model-ru-0.22_1", "version": "kg-stt-1.0"},
  "info_audio": {"seconds": 0, "path": ""},
  "data": [
    {"time_start": 0.0, "time_end": 1.2, "text": "...", "conf": 0.0}
  ],
  "words": [
    {"start": 0.0, "end": 0.4, "word": "...", "conf": 0.0}
  ]
}
```

4. `post_records_queue` + обработка ошибок (`error=True`).  
5. Логи, restart, 1 воркер → потом N.

**Проверка «хотели → сделали»:**

| Хотели | Проверка |
|--------|----------|
| Офлайн | Нет вызовов наружу при STT |
| Полный текст | В карточке очереди виден весь текст фрагмента |
| Тайминги | У сегментов есть start/end; seek в плеере |
| РЛК | Запись привязана к конкретному визиту |

**Нужно от вас:** доступ STT-ПК к файлам аудио портала (путь/UNC), подтверждение что `refresh_queue_recognition` крутится по расписанию.

### Этап 3 — Чек-лист и тематики со склонениями (R2)

**Хотели:** всё ли предложено; на каких фразах сработало; подсказки.

Задачи:

1. Движок матчинга: лемматизация (pymorphy2/natasha) + фразы тематик + порог + синонимы.  
2. Сущность срабатываний: тематика, вопрос, цитата, `time_start/end`, score, auto/manual.  
3. Заполнение внутреннего чек-листа KG (не CVC-таблицы).  
4. UI: баллы, подсветка в транскрипте, подсказки «не найдено: трейд-ин».  
5. Ручной override контролёром.

**Проверка:**

| Хотели | Проверка |
|--------|----------|
| Предложено ли X | Пункт чек-листа зелёный/красный |
| Где сработало | Клик → место в тексте/аудио |
| Склонения | «трейд-ином» ловит фразу «трейд-ин» |
| Подсказки | Список незакрытых пунктов |

**Нужно от вас:** эталонный чек-лист ОП (пункты + примерные фразы-триггеры).

## 7. Критерии успеха продукта

1. По любому пилотному РЛК с диктофоном есть **полный текст с таймингами**.  
2. По чек-листу видно **что предложено / не предложено**.  
3. По каждому срабатыванию — **фраза и время**.  
4. Есть **подсказки** по пробелам скрипта.  
5. Новые слова можно **добавить в контур обучения** без вендора CVC.  
6. Всё **офлайн** на своей инфраструктуре.

## 8. Бонус: менеджер vs клиент в моноканале

В mono **нет** двух физических каналов (в отличие от телефонии L/R). Варианты по возрастанию сложности:

| Подход | Идея | Плюсы | Минусы |
|--------|------|-------|--------|
| A. Эвристики роли | Длина реплик, вопросы, лексика скрипта менеджера | Дешево | Неточно |
| B. Diarization без имён | pyannote / simple clustering → Speaker 0/1 | Разделяет голоса | Не знает, кто менеджер |
| C. Enrollment голоса менеджера | 30–60 сек образца с портала → embedding → match | Привязка к менеджеру | Нужны образцы, шум зала |
| D. Стиль + B/C | Слова чек-листа чаще у менеджера + голос | Лучше в салоне | Калибровка |
| E. WhisperX / pyannote offline | Сильная diarization | Качество | GPU, лицензии, объём |

**Практичная стратегия для проекта:**

1. R1–R2 — **без** ролей (весь текст).  
2. R5 pilot — diarization → «Спикер A/B» + правило: спикер с большей долей скриптовых фраз = менеджер.  
3. Если есть стабильный диктофон у менеджера — enrollment (C).

Честно: в шумном салоне mono diarization **никогда не будет 100%**; для чек-листа «было ли сказано» часто достаточно текста без ролей.
