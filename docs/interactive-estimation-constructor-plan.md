# Конструктор правил интерактивной оценки

Статус: согласованная концепция, реализация ещё не начата.

Дата фиксации: 16.07.2026.

## Цель

Заменить жёстко зашитый в `eco.views.estimations_price_calculation()` выбор работ на
настраиваемую систему:

```text
Осмотр на схемах
→ нормализованные факты
→ правила
→ шаблоны работ
→ маршрут исполнения
→ версионный прайс
→ предварительный план
→ согласование
→ подготовка plan/fact
```

## Зафиксированные решения

1. Осмотр делится на три блока:
   - внешний осмотр;
   - внутренний осмотр;
   - диагностика.
2. Все физические повреждения отмечаются на соответствующих схемах.
3. Точка на схеме не равна физическому повреждению.
4. Одно повреждение может иметь несколько маркеров на разных видах автомобиля.
5. Правила работают с нормализованными повреждениями, а не с координатами.
6. Шаблон содержит работы, материалы, детали и подрядные услуги.
7. Правило определяет, что требуется сделать.
8. Маршрут определяет, кто выполняет работу.
9. Прайс определяет стоимость выбранного маршрута.
10. Ценовые группы динамические и версионируемые.
11. Согласованный расчёт сохраняется неизменяемым snapshot.
12. Изменение фактов, правил, маршрута или цены создаёт новую ревизию.

## Осмотр и повреждения

### Канонический элемент

Один элемент может иметь полигоны на нескольких схемах:

```text
BodyElement: windshield
├── Polygon: вид спереди
└── Polygon: вид сверху
```

### Физическое повреждение

```text
DamageObservation #501
├── element: windshield
├── damage_type: crack
├── quantity: 1
├── severity
├── size / measurement
├── photos
├── marker: вид спереди
└── marker: вид сверху
```

Правило получает одну трещину, а не две точки.

### Справочник типов отметок

Текущие строки и коды (`царапина`, `vmyat`, `carap`, `rzav`, `replace_add` и другие)
становятся записями справочника типов отметок.

Тип отметки содержит:

- стабильный код;
- раздел осмотра;
- категорию: повреждение, состояние, измерение, комплектация;
- поддержку количества;
- поддержку тяжести;
- поддержку размера/площади/значения;
- обязательность фотографии;
- допустимые элементы схемы;
- порядок и активность.

Действия «заменить» и «полировать» в перспективе должны становиться результатом правила,
а не исходным повреждением.

## Дополнительные факты оценки

В правилах должны поддерживаться:

- тип или несколько типов кузова;
- группа кузовов;
- ценовая группа;
- подразделение;
- тип двигателя;
- тип КПП;
- возраст автомобиля;
- тип краски;
- технология «под прибор»;
- количество и тяжесть повреждений;
- результаты толщиномера;
- камера лобового стекла;
- обогрев лобового стекла;
- проекция/HUD;
- датчики и особенности комплектации;
- статусы диагностических систем;
- признаки салона и оборудования.

Тип краски и «под прибор» являются разными измерениями. Автомобиль может быть
перламутровым и одновременно требовать покраски под прибор.

## Справочники

### Работы

Использовать `RefCarPreparationWork`:

- стабильный код;
- этап;
- название и описание;
- нормативное время;
- активность и порядок.

### Материалы

Развивать `RefPreparationMaterial`:

- категория;
- производитель;
- артикул;
- единица измерения;
- технологические потери;
- складской учёт;
- допустимые аналоги.

Цена материала хранится в прайсе, а не в самом справочнике.

### Детали

Создать справочник деталей:

- код и категория;
- название;
- артикул/OEM;
- производитель;
- оригинал/аналог;
- совместимость;
- характеристики;
- активность.

Примеры деталей: стекло, крыло, дверь, фара, аккумулятор.

Примеры материалов: краска, грунт, лак, клей, праймер, наждачная бумага.

Для стекла учитываются камера, обогрев, HUD, датчик дождя и другие характеристики.

### Подрядные услуги

Отдельный справочник услуг и исполнителей:

- услуга;
- подрядчик;
- договор;
- срок действия;
- SLA;
- состав пакета;
- включённые материалы и детали.

## Шаблон операции

Строки шаблона имеют один из типов:

```text
WORK      — работа и нормочасы
MATERIAL  — материал и плановый расход
PART      — требование к детали
SERVICE   — подрядная услуга
```

Для строки задаются:

- количество или формула количества;
- нормочасы;
- обязательность;
- порядок;
- область: повреждение, элемент, операция или автомобиль;
- условие включения;
- ключ технологической потребности для дедупликации.

Пример «Замена лобового стекла»:

- демонтаж;
- подготовка проёма;
- стекольный клей;
- праймер;
- совместимое стекло;
- калибровка ADAS при наличии камеры.

## Правило

Правило содержит:

- раздел осмотра;
- элементы или группы элементов;
- типы или группы кузовов;
- ценовые группы;
- повреждения и количество;
- тяжесть и размер;
- тип краски;
- технологию «под прибор»;
- комплектацию;
- диагностические признаки;
- приоритет;
- группу взаимоисключения;
- область применения;
- результирующий шаблон.

Режим ценовых групп:

- `ALL` — все текущие и будущие группы;
- `SELECTED` — только выбранные;
- `EXCLUDED` — все, кроме выбранных.

Внутри одного поля действует ИЛИ. Между разными группами условий действует И.

Порядок выбора:

1. Приоритет по убыванию.
2. Специфичность по убыванию.
3. Стабильный идентификатор.
4. Suppression и exclusive group.
5. Дедупликация по coverage key.

Неразрешимый конфликт одинаковых правил блокирует публикацию.

## Маршрутизация

Правило не должно дублироваться только из-за другого исполнителя.

Для подразделения и категории работ задаётся:

- собственный цех;
- внутренний централизованный цех;
- подрядчик;
- свой цех с резервным подрядчиком;
- ручной выбор.

Пример:

```text
Покраска    → собственный цех
Стёкла      → подрядчик
Химчистка   → подрядчик
Слесарка    → собственный сервис
```

Свой цех рассчитывается по нормочасам и материалам. Подрядчик может иметь
фиксированную пакетную цену.

## Ценовые группы и прайс

Ценовая группа является строкой справочника, а не колонкой таблицы.

Запрещено создавать поля вида:

```text
price_200
price_400
price_1200
```

Нужны:

- версия схемы ценовых групп;
- диапазоны и период действия;
- версия прайса;
- строки прайса.

Строка прайса содержит:

- объект цены: работа, материал, деталь или услуга;
- исполнителя;
- подразделение;
- ценовую группу;
- тип кузова;
- тип краски и технологию;
- ставку, фикс или цену единицы;
- период действия;
- признак резервной цены.

Изменение границ ЦГ или стоимости создаёт новую версию.

В оценке сохраняются:

- исходная стоимость автомобиля;
- ЦГ;
- версия схемы ЦГ;
- версия прайса;
- исполнитель;
- каждая применённая цена.

## Бизнес-процесс

1. Администратор ведёт справочники.
2. Редактор схем связывает полигоны с каноническими элементами.
3. Технолог собирает шаблоны.
4. Технолог создаёт правила.
5. Экономист создаёт схему ЦГ и прайс.
6. Руководитель подготовки настраивает маршруты.
7. Simulator проверяет покрытие, конфликты и отсутствующие цены.
8. Версия проходит проверку и публикацию.
9. Оценщик проводит внешний и внутренний осмотр.
10. Диагност проводит диагностику.
11. Система строит объяснимый preview.
12. План проходит согласование.
13. Специалист подбирает конкретные детали и предложения.
14. Согласованный snapshot передаётся в `CarPreparation`.
15. Исполнители фиксируют фактическое время и расход.
16. ОТК принимает работы или назначает повторный осмотр.
17. Аналитика сравнивает plan/fact и помогает корректировать нормы и цены.

## Статусы

Настройки:

```text
Черновик → На проверке → Опубликовано → Архив
```

Оценка:

```text
Черновик → Осмотр завершён → Рассчитано
→ На согласовании → Согласовано → Передано в подготовку
```

Деталь:

```text
Требуется подбор → Подобрано → Цена подтверждена
→ Зарезервировано → Заказано → Получено
```

Работа:

```text
Ожидает → Запланирована → Назначена → В работе
→ На контроле → Принята
```

## Ошибки и исключения

- Нет правила: факт помечается непокрытым.
- Нет цены: запрещены молчаливый ноль и соседняя ЦГ.
- Нет детали: создаётся требование на подбор.
- Нет маршрута: расчёт блокируется.
- Конфликт правил: публикация блокируется.
- Изменился прайс: старая оценка не пересчитывается.
- Скрытый дефект: создаётся новая ревизия и повторное согласование.

## Производительность

1. Контекст оценки загружается пакетно.
2. Внутри цикла правил нет ORM-запросов.
3. Опубликованные правила компилируются заранее.
4. Индексы правил:
   - раздел;
   - элемент;
   - тип кузова;
   - ценовая группа.
5. Прайсы загружаются одним batch-запросом.
6. Пересчитывается только изменённый канонический элемент.
7. Preview кэшируется по hash фактов и версиям настроек.
8. Согласованная оценка читается из snapshot без повторного расчёта.

## Критерии готовности MVP

- Все используемые типы отметок имеют стабильные коды.
- Все повреждения вводятся через схемы.
- Количество повреждений отделено от количества маркеров.
- Правила не используют магические PK.
- Шаблоны раскрываются до четырёх типов строк.
- Все применимые ЦГ и маршруты покрыты ценами или явным резервом.
- Preview объясняет выбор каждого правила.
- Двойной учёт работ исключён.
- Snapshot не меняется после публикации нового прайса.
- Новый расчёт прошёл shadow-сравнение на пилотных подразделениях.
